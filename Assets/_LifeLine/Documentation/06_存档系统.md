# 存档、继续游戏与恢复边界

## 玩家流程

本地双人共用一个航程存档槽。第1日新局初始化后，在白天完成第一次自动保存；以后每个新day在每日地图刷新完成后，白天自动存一次。2026-11-18后续批次以`automaticSaveDelay=.25`秒将自动保存错开地图刷新／初始化帧，手动保存仍立即执行；详见[16_拾取救助与昼夜优化.md](16_拾取救助与昼夜优化.md)。同一天不会因反复读档、暂停或重新打开设备而重复自动保存。

ESC暂停菜单中“手动存档”覆盖同一个槽，包括之前的自动存档。手动保存同时标记当天已存，防止该日随后一次自动保存覆盖手动进度。成功与失败会直接显示在暂停卡上。返回主菜单后，有有效存档才显示“继续游戏”；没有或无效时隐藏整个按钮。继续恢复存档时刻，不补离线时间，也不重新发放开局材料。

“开始本地双人”及“重新开始”明确开始新航程；新航程第1日自动保存会替换原槽。返回主菜单本身不额外存档，保留玩家选择的最近自动/手动进度。

## 文件与配置

- 默认文件：`Application.persistentDataPath/LifeLine/save-v1.json`。
- Windows通常为 `%USERPROFILE%/AppData/LocalLow/LifeLine Team/LifeLine/LifeLine/save-v1.json`，以运行时 `GameSaveManager.SavePath` 为准。
- `pathOverride` 留空使用默认位置；开发测试可指定独立文件，不触碰正常存档。
- `GameSaveManager` 在主菜单和Gameplay分别有场景实例；不使用跨场景保留的GameSession。
- Gameplay的 `GameSession.autoStart=false`，管理器明确选择新局或读档，避免Start时新局初始化覆盖已恢复数据。

文件有版本号、原始payload JSON的SHA-256校验和与基本语义验证；最大读取16MiB。先写同目录`.tmp`、Flush并重新读取校验，再原子替换主文件，旧文件保存在`.bak`。备份是开发恢复资料，不会在主文件损坏时静默加载不同进度。失败不会覆盖有效主槽，读档失败也不会暗中新开局并自动存掉旧文件。

主菜单会显示已有文件的校验错误并隐藏继续；没有存档时保持安静。加载过程中发现配方缺失、昼夜配置不兼容、生成物ID失配等，保持暂停并显示原因，可返回菜单或明确重新开始。

| 制作 | 稳定配方id、jobId/下一个id、所属角色、进度/耗时、音符/判定、命中次数、repairApplied累计已修复量；恢复同一个Manager队列 |
| 维修 | 已付费用授权、引擎四故障清理/匹配结果、版本、电路连线和导流拼图旋转进度 |
| 世界 | 当日种子、每个确定性saveId的物资剩余量/已采集状态、箱内准确材料、位置/挂载状态、门开关/破坏状态；hasHidingSpots及藏匿点位置／房间编号／范围快照 |
| 碰撞绳与地图 | 当前潜水员/吊运货箱墙角接触点、coordinateVersion；船上坐标规范化，旧共享地图档自动转换 |
| 动态物资 | 跨日挂载箱与昏厥失物使用持久id，重复读档不会复制货箱 |
| 战斗 | 存活敌人的生命/变异、AI阶段与计时、深影已命中次数/三攻击索引/阶段/固定瞄准点、射矛位置/已飞距离/10m上限/目标/召回状态 |
| 航程 | 自然时间、当前日、电台/主线、救援进度、天气、尚未落地的预警种类/固定坐标/剩余时间/半径/伤害、影子当夜刷新/退场与故事记录 |

不把GameObject实例ID、SO对象引用或开发人员的调参资产写成存档引用。配方按稳定id重新解析；世界按当日种子重建后恢复状态。调整配方id、地图算法/尺寸、昼夜长度或版本时，应考虑旧档兼容或明确开始新局，不能把不兼容文件当作成功读档。

建筑随机点位更新后，同日读档恢复保存的藏匿点快照，不重新抽取。旧档保留原货箱ID、内容和挂载状态；没有藏匿点快照时为正在旧点位藏匿的角色保留保护位置。新增箱子不在读取旧档时补发，跨日才应用完整新区间。具体数量、停用ID记录和调参见[18_建筑货箱与藏匿点随机分布.md](18_建筑货箱与藏匿点随机分布.md)。

## 读档时释放的临时操作

读档完成后关闭设备、设置和换绑面板，释放舵手、按住的输入及进行中的4秒扶起动作。手动绞盘需要重新打开设备；已授权的电动自动回收仍保留。角色不会因此自动登船，背包不隐式卸货。正在制作的任务继续保留已消耗材料和进度。

这些瞬态操作不作为长期进度；恢复后仍由原来的物理、制作和救援系统推进。船舶费用与Tuning配置不从存档反向覆写Inspector。

## 测试与维护

独立测试在 `Tests/EditMode/PersistenceTests.cs`，使用临时独立目录；覆盖真实JSON往返、原子覆盖与备份、同日防重、手动先于自动、继续不重置、损坏/缺失配方保护、战斗阶段、精准货物和重复加载。实际通过结果与场景验证以00文档最终记录为准。

2026-11-16实际Unity存档测试9/9通过（全部EditMode合计24/24）。其中2项特意覆盖未打开过滤器时的null与场景序列化空数组：它们视为未生成，读档后首次交互才生成；已生成的管道旋转进度原样保存，只有一侧数组缺失的损坏状态会被拒绝。实际主菜单至继续游戏链及第2日自动保存已验证，不只调用文件工具。

后续P2P模式应由主机保存权威状态，不能让两端独立覆盖同一个航程；当前实现属于本地双人阶段，未接入云存档或Steam同步。

## 白天加长后的旧档迁移（2026-11-17）

新存档附带cycleSeconds/daylightSeconds/duskSeconds。读档按已保存的“天数+当前白天/黄昏/夜晚内的相对位置”映射到当前时钟配置，不把第2天误读成第1天，世界日种子与自动存档日期不变。旧文件缺少时钟字段时按原180秒、白天120.6秒、黄昏23.4秒、夜晚36秒解析。手摇与连续信号的绝对计时同步偏移，其他剩余时长保留。日期与原周期不一致的损坏数据仍拒绝加载。

每箱挂绳接触点分别保存于PickupSaveState.ropeContacts，避免多个箱子读档后共用第一箱的绕墙路线。原顶部cargoRopeContacts只兼容旧档。

F8面板执行修改命令后使用独立developer-test.json；退出测试航程后默认继续仍读取玩家save-v1.json，不会让测试跳日覆盖正式存档。详见08。

## 本轮兼容与失败恢复

旧默认绳长20/26/34/54m按保存等级映射至28/44/54/74m，手工自定义长度保留。旧默认T2/T3氧气100/130s迁移到115/145s，补入增加的15s余量；非标准自定义氧气值保留。浅水追击鲨鱼读档允许回到原位置，新生成仍需25m以下。预警使用逻辑水下坐标，随船舱地图原点转换显示，读档恢复剩余倒计时。

两人均失去行动能力或船体归零时进入失败面板，读取上个存档或返回主菜单；失败不会自动覆写槽，也不会自动复活清仓。读取按钮复用主菜单的RequestContinue流程，没有有效槽则禁用。

最新存档包含balanceVersion=1与routeDistance。旧90m存档保持船的航线百分比、船上局部坐标、物资与设备进度；旧半单位承伤乘2。保留挂箱和遗失货箱标记及准确内容，并恢复高效燃油机、鸟操作打断目标。旧船长和潜水员氧气映射到50与50/75/120/150秒，保留剩余比例及潜水员有效氧气鱼获加成。详细规则、边界和迁移入口见13。历史T2/T3氧气迁移段仅描述前一轮版本。


## 2026-11-18 设备进度与教程兼容

最新细节见[15_设备建造与新手引导.md](15_设备建造与新手引导.md)，覆盖早期设备默认存在、过滤器成本／增益、探照灯等级与教程描述。新游戏70/100耐久、0电，六类设备按制造／升级／打捞解锁；旧档保留既有耐久和电力，设备版本0将原已存在的发电机、维修台、过滤器视为已安装，旧探照灯0/1只迁移一次为新1/2。

`GameSaveData.hasTutorial`明确记录教程数据是否存在。Unity的JsonUtility对内联可序列化类做JSON克隆时可能把null展开为默认空对象，因此不能只靠克隆后的`tutorial != null`识别新旧存档。捕获时同时写presence和TutorialSave；恢复前先读取`hasTutorial && tutorial != null`，克隆后缺失则显式置null，交给TutorialProgress跳过旧档基础教程。已有真实教程进度不会被SessionReady(true)重置；旧档仍可显示三类首次事件提醒。首个Day1自动存档在HUD／教程初始化后才捕获，不漏掉新局进度。

射矛枪开工后保存已消费鱼叉，取消不返还，恢复不重复扣除。已取得过滤器后不再日刷新；未取得的特殊打捞记录读档后仍保留设备行为，不变成普通金属。F8当前设备跳过QTE继续使用developer-test.json隔离槽，所有建造／维修授权费用仍正常执行。
